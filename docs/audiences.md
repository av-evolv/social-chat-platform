# Circles and conversation audiences

[#6](https://github.com/av-evolv/social-chat-platform/issues/6) supplies relationship and audience-policy management through OAuth-protected `/v1/social` routes. Circles are independent from conversations. Creating or administering a circle grants no access to unrelated conversations. A registered participant can share their participant ID as a contact code; invitations require acceptance before becoming active membership. No email or global account directory is exposed.

Circle members have OWNER, ADMIN or MEMBER roles. Only owners change roles; administrators can manage non-owner members. An explicit edit cannot remove the last active owner. Each mutation requires the current string `expected_revision`; clients refresh after a conflict. Create requests require UUIDv7 `operation_key` values. Repeated creates return the original object ID with its current authorized metadata/revision only after current authorization succeeds; changing the payload with the same key conflicts. Object tombstones prevent replay from reviving deleted resources.

Conversation audience sources are `{type: USER | CIRCLE | EVENT, id, operation: INCLUDE | EXCLUDE}`. Resolution canonicalizes participant aliases, unions includes and then subtracts exclusions. All contributing provenance is retained. Self-leave records a separate durable exclusion, so replacing the audience cannot silently re-add someone. A self-left participant can see only their minimal prior conversation reference and its current revision to request rejoin; rejoining still requires eligibility in the current policy. Source administration and conversation roles remain independent. Audience edits retain the caller’s management eligibility; explicit self-leave is the supported withdrawal action. Administrators cannot exclude any eligible owner.

All account devices currently lack cryptographic admission. Consequently, all eligible conversation memberships remain PENDING and the content/send gate remains CLOSED. Explicit eligible conversation owners/administrators have a narrow bootstrap permission to manage audience metadata; ordinary pending participants cannot read the roster or private content. No plaintext conversation titles, messages or media are introduced. The client labels resources using creation dates and abbreviated identifiers. Private display content and encrypted device admission are owned by #9/#10.

## Primary transaction boundary

`SocialStore` operates on the primary, with lock order: create-operation key, shared OAuth grant lock, actor account row, then the social policy advisory lock. OAuth checks the current token, consent, binding and provider session again on the same connection. Account state, session and device are revalidated after the account lock. The shared grant lock orders protected operations against revocation; artifact row locks protect the provider session. Policy changes and protected callbacks share the policy lock, so a removal committed first denies the subsequent operation. A write authorized first may commit before removal. Bounded transaction retries handle PostgreSQL serialization/deadlock failures.

The initial policy lock is deliberately coarse and serializes policy operations. It favors demonstrable correctness at M1 scale. #19 must measure workload, add quotas/retention and review finer locks before claiming production scalability. Responses already delivered cannot be recalled. `withConversationAccess(..., 'content', ...)` fails closed until #10 provides trusted device admission; it is an internal integration boundary, not a public placeholder messaging endpoint.

Identity session issuance, recovery, device revocation and logout call `invalidateParticipant` inside the identity transaction after locking the account. This closes the window between identity changes and audience generation refresh. Event and alias integrations must follow the same lock order and invalidate affected policy before committing. Upstream removals proceed even if they remove the final eligible conversation owner; the orphaned conversation freezes management instead of blocking revocation. Membership intervals and generation changes are persisted; these application generations are not MLS epochs or signed admission evidence.

## Event and guest integration

`EventSourceAdapter.resolve(db, eventId)` is an internal server adapter returning an authoritative source version, currently eligible participants and principals permitted to inspect its roster. It uses the supplied transaction connection. The production default returns unavailable, so EVENT sources fail closed until #12 supplies the event authority. Clients cannot submit event rosters or versions. An unavailable EVENT authority closes the entire affected policy, including exclusion rules, until authority returns; a versioned authoritative empty roster is distinct from unavailable data. Real SQL fixture tests exercise source updates, filtering and overlapping provenance; they do not constitute a shipped event service. Merely associating an event with a conversation grants no audience access.

Identity migration 2 creates `participant_aliases`. #7 owns verified guest claims, alias creation and conflict policy. There is no public alias mutation endpoint in #6. Claim transactions must acquire the policy lock and reconcile alias effects before commit. Canonicalization failures or cycles deny access. Historical participant IDs remain stable attribution keys.

## API and verification

GET `/v1/social/circles` and `/conversations` list accessible metadata; GET `/:id` returns a policy-filtered resource. POST creation takes `operation_key` (plus `sources` for conversations). Circle actions are `invite`, `accept`, `leave`, `remove`, `role`, `delete`; conversation actions are `audience`, `role`, `leave`, `rejoin`, `delete`. POST `/preview` takes `sources` and optionally `conversation_id` for an authorized edit context. That context permits retaining known USER sources and current eligible participants after a shared circle ends; arbitrary new contact guesses still fail. CIRCLE/EVENT references continue to require current source-roster authority and `circles:read`/`events:read` respectively, including in contextual previews. Inaccessible sources may be removed without exposing their raw rosters. Mutations use `expected_revision`, `participant_id` and `role` as appropriate. Circle scopes are `circles:read/write`; conversation and preview scopes are `conversations:read/write`. Scopes never substitute for object policy. Unauthorized object identifiers return 404, invalid credentials 401, insufficient scope 403, stale revisions/conflicting operation keys 409.

Run API tests with `OAUTH_TEST_DATABASE_URL` pointing at PostgreSQL18. They use isolated schemas and real competing connections to exercise source removals, identity revocation, OAuth grant revocation and protected-operation ordering. The universal client supports relationship management and audience preview; its English strings are included in #42's English/French localization scope.
