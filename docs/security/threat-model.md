# Larynx security contract

Status: M0 design decision, 2026-09-14. Tracked by [#3](https://github.com/av-evolv/social-chat-platform/issues/3); implementation and release evidence live in the linked feature issues below. This document specifies required behavior; the foundation shell does **not** yet implement product E2EE, identity or authorization. Read with the [domain contract](../domain-contracts.md) in #2. The [compatibility report](openmls-spike.md) selects OpenMLS for the next integration stage with explicit limits.

## Assets and trust boundaries

Protect private message/event/media plaintext, device and recovery secrets, group state, authenticated authorship, membership and local indexes. Keep OAuth grants, identity verification and storage credentials separate from encryption keys. Conversation is the messaging group; a circle, event association or server administrator is not a decryption principal.

| Threat / boundary | Required control | Residual limit |
| --- | --- | --- |
| Database, object storage, push provider or delivery server compromise | Only ciphertext and necessary routing metadata leave clients; authenticate message context and device credentials; transport TLS and least-privilege storage | Service can observe metadata, withhold/reorder data or deny service |
| Malicious member, revoked device, conflicting memberships | Exact device roster; independent server authorization and client admission validation; epoch changes and fail-closed sending gate | Prior plaintext, keys, screenshots and colluding recipients cannot be recalled |
| Authentication server substitutes a device key | Existing trusted-device approval and user-visible identity verification; pin verified credentials; visibly reset identity after total key loss | First contact remains trust-on-first-use unless users verify out of band; no key-transparency claim |
| Browser XSS, compromised app/update, rooted or unlocked device | Minimize executable dependencies, strict CSP and escaping, protected storage, short secret lifetimes; cryptographic work behind platform adapter | Code running as the client can read decrypted content; web delivery service can ship hostile code |
| Stolen OAuth token / malicious third-party app | Audience, client, scope, grant/revocation and primary object authorization on every operation | An authorized app can copy whatever data the user explicitly shares |
| Rollback, replay, partial writes, parallel tabs/devices | Transactional protocol state with inbox/outbox, per-group single-writer serialization, generation checks, replay rejection, bounded resync | A server can fork views or suppress updates; detection/recovery needs integration tests |
| Malformed ciphertext / oversized input | Size and rate bounds before decoding; worker isolation and cancellation; maintained pinned dependencies | E2EE does not prevent abusive recipients or all computational DoS |

Private logs, crash reports, analytics and support exports must exclude plaintext, tokens, signed URLs, identity secrets, content keys and raw crypto state. Disable OpenMLS `content-debug`/`crypto-debug`. User-triggered abuse reporting, if introduced, must explicitly show which decrypted material is sent; no silent plaintext moderation channel.

## Membership, history and devices

Effective conversation participants are the union of explicit INCLUDE sources minus every applicable EXCLUDE source, after canonical participant alias resolution, as defined by #2/#6. Identity claiming is not an automatic global account merge. Circle administration is not conversation access. Each participant has distinct registered devices; each admitted device is an MLS leaf bound to the participant/device credential. A `BasicCredential` byte string alone does not establish that binding.

- A new participant receives messages from accepted cryptographic admission onward. Invites, circle join timestamps and API account creation do not grant old epochs. Rejoining creates a new admission interval with no access to messages from the absence. Explicit history sharing is deferred; it must be a separate visible grant, never an accidental Welcome/backup side effect.
- Enrollment requires authenticated account control **and** approval from an existing trusted device. The first device bootstraps a visible identity; total-device loss follows the reset/recovery policy below. New devices receive current group membership only after approval. Transferring older history to a new device is explicit, limited to that participant's permitted intervals and retention, and cannot restore missed-period keys from another member.
- The primary database atomically updates effective authorization and increments an opaque roster generation. Additions/removals close the conversation application-send gate. A permitted existing device proposes/commits the exact new device roster; recipients verify every credential and change against the authorized generation before accepting. Open the send gate only when that roster is reconciled. MLS epochs and application roster generations are distinct; self-updates may advance only the epoch. Serialize concurrent membership changes, reject stale commits/sends and resync; never silently downgrade to plaintext.
- Removed users/devices immediately lose new API read/download/signing authorization on the primary, even before crypto reconciliation. A stale sender must sync before sending. Rotation protects future epochs; it cannot erase downloaded history. Already issued object URLs remain usable until their expiry (see media below).
- Identity-key changes, resets and newly admitted devices must be visible to affected members. Pin verified identities and require re-verification on reset; do not accept server replacement merely because OAuth authentication succeeded. Key-package validation, lifetime, single-use reservation and duplicate-device rejection belong to #10.

Guest devices participate in the same E2EE model, with a scoped verified guest participant and OAuth client grant. An invitation bearer token alone grants neither membership nor keys. Guests must complete actual device admission; no server decryption fallback. Until protected browser persistence and recovery are implemented, guest secrets stay session-only and closing/losing the session may lose access. Registration preserves stable participant/authorship IDs and does not silently widen history. See #5, #7, #10, #18 and #21.

## Events and media

An event has its own audience and content-key version. Associating it with a conversation grants neither event access nor conversation membership. A client encrypts one versioned event document with a fresh content key and delivers that key through authenticated encrypted channels only to authorized event devices. A conversation-wide key envelope is permitted **only if every device receiving it is currently in the event audience**; otherwise use explicit authorized-device delivery. Direct attendees are real authenticated crypto devices, not plaintext email recipients.

An event audience removal closes event writes until a new key version and next document revision are created for the remaining audience. Do not distribute an old key to a new participant by default. Audience additions get the explicitly shared current revision, not all historical revisions. Event editor roles control accepted updates independently of decryption; clients verify writer identity/role, revision, object ID, audience generation and key version. MLS transports key envelopes; it does not automatically implement cross-group event authorization. #14 must select and review the concrete envelope/document format before implementation; this is not permission to invent a group protocol.

Each immutable media object gets a fresh random content key, independent of circles or long-lived group secrets. Deliver its key through authorized encrypted message/event metadata. Bind object ID, version, length and chunk ordering to authenticated metadata. Thumbnails and sensitive filenames/EXIF need the same confidentiality. The concrete reviewed streaming/chunked AEAD format is a #15 gate: multipart transport boundaries are **not** automatically safe encryption boundaries. No homemade nonce derivation, nonce reuse on retry, or releasing unauthenticated partial plaintext. Resuming upload must reuse identical ciphertext for an existing part or allocate a new object/key; verify final manifest and authentication before displaying content.

Clients transfer ciphertext directly with short-lived, narrowly scoped S3 signatures. The API authorizes each initiation/part/completion and validates object ownership, total encrypted length and part inventory/checksums before publication. The server cannot inspect E2EE plaintext or attest that client checksums imply benign content. Cap signatures at five minutes and no later than the object's effective expiry; do not promise immediate revocation of issued URLs. SQL deletion marks the object inaccessible and writes a durable outbox record in the same transaction; idempotent workers delete blobs/parts/variants with retries. SQL and S3 are not one atomic transaction. #14/#15/#19 must verify replacement, abandoned upload cleanup and deletion retry behavior.

## Metadata policy

This is an allowlist for private consumer domains; absence from the allowlist means do not send plaintext without a reviewed change. Organiser/enterprise public or managed fields require an explicit separately labelled policy (#23/#26), not a hidden exception.

| Server-visible | Purpose / consequence |
| --- | --- |
| Opaque participant/account/device IDs, identity verification records, public device credentials | Authentication, authorization and routing; server necessarily knows identity/account mappings it verifies |
| Circle/conversation IDs, effective membership sources/roles, event audience IDs and association edges | Object access and synchronization; exposes social graph and event attendance relationships |
| Object/message IDs, author device ID, sequence, roster generation, epoch/header information, revision, ciphertext lengths and receipt timestamps | Ordering, abuse bounds, transport and consistency; exposes timing/traffic patterns |
| Ciphertext checksums, media object/upload IDs, encrypted lengths, part inventory, deletion tombstones and expiry deadline | Storage integrity, quota and retention; media type beyond necessary transport is not assumed private |
| OAuth client/grant/scopes/audience and consent records, IP/access/security logs, opaque push endpoint/ticket | Explicit application control, security and delivery; minimize log retention under #19 |

Encrypted: message bodies and attachment descriptions; private conversation title; event title/description/start/end/timezone/location; media filenames/EXIF/location/captions; event suggestion inputs and outputs. RSVP identity and minimal response status (for example GOING/MAYBE/DECLINED) are server-visible because accepted attendance can drive conversation membership; detailed RSVP answers and notes stay encrypted. This explicitly discloses attendance status to the service. IDs and ciphertext sizes do not provide anonymity. Hashing low-entropy identity values is not anonymization.

Calendar ranges, text search (`tsvector` is only for deliberately server-visible text), photo association and event-detection AI run over decrypted local data. The server can sync opaque event revisions and send generic change notifications; it cannot query encrypted event times for scheduled reminders. Clients schedule private reminders locally. Push payloads contain only opaque IDs/generic text; OS notification previews are a user preference. No conversation plaintext enters analytics, model training or remote inference by default. Any later cloud inference requires explicit scoped opt-in and a visible data-sharing boundary (#13).

## Local persistence and recovery

Native: SQLCipher stores private records/indexes and protocol state; protect its random key using OS-backed SecureStore, with an explicit lock/background policy. Browser: encrypt sensitive IndexedDB values/indexes behind the shared repository interface; begin with session-only unlock secrets, then add user-approved trusted-device/recovery unlock. Do not store a decrypting key beside ciphertext, claim browser storage is a hardware keystore, or use localStorage for bearer tokens. Key protection is separate from message E2EE.

Serialize crypto state mutation per group, including multiple browser tabs. Persist inbox acceptance/replay state, protocol ratchets and pending sends atomically before acknowledgement/transport reuse. Do not restore live ratchets blindly from stale snapshots. The spike's in-memory provider is not production storage; tamper/retry, crash recovery, concurrent receive/send, disk-full and backup rollback need #9/#10 tests. Only cache plaintext while needed in process memory; JavaScript zeroization cannot be guaranteed. Logout removes local keys, private databases, caches, previews, pending notifications and AI-derived artifacts; revoke device grants and queue remote removal where connected. Offline remote wipe is best effort, never guaranteed. SecureStore deletion/reinstall/biometric behavior must be tested on real devices, not inferred from SQLCipher alone ([Expo storage documentation](https://docs.expo.dev/versions/latest/sdk/securestore/)).

Account recovery restores login, **not** old decryption keys. Prefer explicit encrypted history backup protected by a high-entropy user-held recovery secret; server stores ciphertext only. #18 must select a reviewed backup format, authenticate owner/version and prevent rollback, protect recovery material independently of OAuth/email, and test loss/rotation. Do not back up live protocol ratchets for silent replay; re-admit recovered devices at a new epoch and restore only authorized retained history. No password-derived recovery format is selected here. If no trusted device or valid recovery secret remains, reset cryptographic identity visibly and accept loss of inaccessible history. Never promise email reset recovers E2EE data. Export/backup retention must not resurrect expired content.

## Retention and future ephemeral features

MVP private content persists until explicit deletion or an explicit product retention policy. No disappearing/view-once guarantee is shipped by this document. Record server deletion immediately as a tombstone; suppress reads/resync resurrection and enqueue physical object removal. Define and test backup retention/restore filters and maximum deletion lag under #19 before release; do not invent a legal retention duration in a technical foundation.

Future disappearing messages and timed/view-once media (#27) need authenticated absolute expiry, a server deadline for access/deletion, local cleanup of keys/previews/indexes/caches/AI suggestions and a multi-device consumption policy. Client clocks, offline recipients, backups, pre-fetched URLs and dishonest clients prevent guaranteed erasure or exactly-one human viewing. Keep media out of reusable caches where possible; view consumption must be atomic on the authoritative service with explicit offline behavior. Expiry means best-effort access/key cleanup, not protection against screenshots or retained plaintext. BeReal-style gamification (#28) is opt-in and must not create an unannounced camera, location or notification collection channel.

## OAuth boundary

Every product API call uses an OAuth token bound to client, subject, audience and scopes plus current object-level authorization from the primary. Browser/native public clients use authorization code with PKCE S256, exact registered redirects and short access lifetimes; #4 specifies refresh rotation/reuse detection, consent and revocation. Health probes and protocol bootstrap endpoints follow their separately scoped public contract, not an invented token prerequisite loop. Realtime uses an authenticated handshake or short-lived scoped ticket, never a long-lived bearer URL ([OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html)).

An OAuth scope grants an operation, never possession of an E2EE key. First-party clients get no bypass. Third-party apps initially receive permitted ciphertext/server-visible data only; plaintext access requires separately admitting an explicitly labelled app device to the relevant crypto audience and informed user consent, or explicit client-side export. Do not automatically enroll apps or return recovery/group keys from token endpoints. Revoking a grant stops new API access and triggers any app-device removal/rotation, but cannot recall exports. Keep public release blocked by #30 until malformed auth/deep-link parsing is resolved.

| Issue | Security acceptance gate |

| #15 / #16 | Reviewed authenticated media format; nonce/retry safety; tampered/reordered/truncated chunks; no plaintext upload; signature expiry and cleanup |
| #18 / #19 / #21 | Total key loss, verified enrollment, guest session loss, backup/restore expiration, SQL deletion outbox retry and real revocation |
| #20 | Real iOS/Android/Hermes and supported-browser tests, cryptographic integration review, current upstream advisories and dependency graph review; privacy claims match delivered behavior |

The reference security properties and their authentication/metadata limits come from [MLS RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html). Application policy, storage, delivery and user trust decisions above are Larynx requirements, not guarantees supplied by MLS alone.
